# Design decisions

Short records of the main choices and why they were made. Results referred to here are
in `artifacts/` (generated by code); this file states no result numbers of its own.

## PostgreSQL with pgvector instead of a vector database

One store holds the NTSB tables, passages, embeddings (HNSW index), lexical statistics,
evaluation inputs and API runs. The leakage filters (`event_date < before_date`,
`event_id <> target`) are plain SQL in the same query as the vector search, so no result
can come back from a store that forgot to filter. A separate vector database would add a
second copy of the data, a sync step and a second place where that filter must be right.
Schema changes stay plain SQL migrations. Cost: pgvector filtered HNSW scans need
`hnsw.ef_search` and iterative scans to fill the candidate list; `causetrace.retrieval`
sets both.

## PostgreSQL full-text search instead of Elasticsearch

`tsvector` columns with a GIN index, an OR query of the 30 most salient query terms
(tf-idf over history passages only) and `ts_rank_cd` with length normalization. It runs in
the same database and the same transaction as the dense search and shares its leakage
filter. Elasticsearch would score better out of the box (BM25) but is another service to
run, secure and keep in sync. Cost: an OR query built from a whole narrative matches nearly
every passage, so `ts_rank_cd` over the matches dominates search latency. The query now
runs with more parallel workers (same SQL, identical ranking, checked by a test on every
held-out fixture packet). A faster exact top-k would need an upper bound on `ts_rank_cd`
to skip documents, which was not worth the risk of changing the ranking.

## Reciprocal rank fusion

Dense and lexical scores are on unrelated scales (cosine similarity, `ts_rank_cd`). RRF
(k = 60) fuses by rank only, so it needs no calibration or tuning data, and ties are broken
deterministically (best single rank, then id). It has the highest held-out Label
Recall@10 in `artifacts/retrieval_results.md`, and it is the mode the CI gate guards.

## Cross-encoder reranking, and rrf for long queries in the agent

`cross-encoder/ms-marco-MiniLM-L6-v2` rescores the fused top 50. It is trained on short
web questions, and each (query, passage) pair is cut to 512 tokens with at most 192 for
the query. It clearly helps short known-item questions, but on held-out packets (whole
narratives) it ranks worse than plain rrf (`artifacts/retrieval_results.md`). The agent
therefore reranks only queries under `AgentLimits.rerank_max_words` (60) words; longer
queries, such as the packet fallback, use rrf. In the API a reranker failure falls back to
rrf and says so; in evaluations it raises, so rrf is never scored as reranked.

## Date-based split

Held-out = `ev_date >= 2024-01-01`, history = earlier (`causetrace.split`). A random split
would let a model retrieve or be tuned on investigations written after the incident it is
judged on, which is impossible in use. Every search uses `corpus_cutoff(ev_date)`, capped
at the split date, so held-out events never enter the corpus. Known gap: the export has no
final-report date, so `ev_date` stands in for when a report became available
(`docs/DATA_LEAKAGE.md`).

## Label level

A label is `category-subcategory-section` of a finding with `cm_inPc = 'T'` (cited in the
probable cause), across all aircraft of the event. Full finding codes and modifiers are too
sparse to recur across events, which retrieval needs; the category alone is too coarse to
be useful. The taxonomy lists only codes seen as causes in history events, so a held-out
event cannot add a code; gold labels outside it count as misses and are reported.

## Tuning cut-offs on 2023 dev events

A 20-case held-out pilot showed the LLM systems over-predicting. Held-out results must not
drive changes, so the confidence cut-offs of the LLM systems (and the kNN vote cut-off and
frequency-prior k) are tuned on 2023 history events, each searched before its own date.
The pilot's numbers are not reported (dated note in `docs/EVAL_PROTOCOL.md`).

## Claude Haiku only, within a $10 budget

Every LLM system runs `claude-haiku-5-5` through `AnthropicProvider` (no fallback model
mid-run), so systems differ only in what they are given. A `SpendTracker` checks `MAX_USD`
(default $10) before every call; a run stops cleanly at the limit or when Claude is
unavailable (timeout, overload) and resumes from its cache. The cost of the full comparison
is in `artifacts/causal_results.md`. One run with default sampling; larger models were not
compared.

## Bounded agent loop

plan, retrieve, check_evidence, one optional extra hop, analyze, verify, one optional
revision, then answer or abstain. `AgentLimits` caps planned queries (3), extra hops (1),
revisions (1), passages (10), findings (5) and tokens per run (80,000), and LangGraph's
recursion limit guards against a routing bug. An unbounded "search until confident" loop
would make cost and latency unpredictable and hard to evaluate. Abstaining is a valid
answer: only findings with a citation the verifier judged SUPPORTED are returned.

## Serving: fail cleanly, keep answers grounded

The API answers 503 when the LLM or the database is unavailable rather than hanging (Claude
requests time out after `CAUSETRACE_LLM_TIMEOUT_S`, default 120 s; the SDK default of 600 s
once stalled an evaluation run). Invalid model JSON is retried once and then treated as no
answer, so the run abstains. Free-text packets are length-capped and checked for
prompt-injection phrasing (a narrow pattern list: NTSB narratives quote ATC phrases such as
"disregard previous instructions"). A finding without a valid citation is dropped, and the
response reports the share kept as its grounding score. Every run is stored with its trace.
